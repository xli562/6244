# 纯仿真项目实验报告

2026 年 11 月 18 日。本轮回答三个问题：之前为什么涨分，代理怎么选出更好的程序，以及同一套工具遇到其他机器人任务时表现如何。

**结论。** 旧任务里，涨分最明显的环节是关抽屉。新加入的 13 项任务里，仿真反馈帮 Codex 把“开炉放煎锅”从 4/40 提高到 38/40。多任务程序仍难应付新指令：四项完全留出的任务中，Codex 和 Claude 各跑了 200 次，都没有完整成功。现在能区分有些任务卡在“没读懂”，有些卡在“第二件物体没放好”。

## 为什么之前涨了分

**从失败记录看，Claude 第二版最明确的进步是关抽屉。** 在原先第二批 100 个仿真布局上，8 个程序共做 800 次。多布局第一版成功 632 次，第二版成功 657 次，净增 25 次。“抽屉没关好”从 74 次降到 31 次，少失败 43 次；与此同时，“没拿起杯子”从 28 次增到 40 次。第一版与第二版的平均差是 3.1 个百分点，跨开发轮次和场景的 95% 区间为 −6.1 到 +13.2 个百分点。[原始分组成绩](../sim/outputs/main/summary.md)

**噪声提示对某些程序很有用，但光增加噪声不会稳定涨分。** 我把两家代理各 3 份相同起稿分成四组。每组得到相同的 8 个开发布局、相同的修改机会。只有开发噪声是否变化、是否告诉代理误差大小这两处不同。24 份修改全部冻结后，再让它们做同样的 64 个新布局。每格共 192 次试跑，统计上的起稿数是 3。下面是一次修改之后的成功率。[四组逐程序成绩](../runs/noise_factorial/results.json)

| 开发条件 | Claude | Codex |
| --- | ---: | ---: |
| 固定 5 mm，不显示数值 | 84.4% | 7.3% |
| 固定 5 mm，显示数值 | 82.3% | 12.0% |
| 误差在 2.5–10 mm 变化，不显示数值 | 53.1% | 4.7% |
| 相同的变化误差，显示数值 | 83.3% | 5.7% |

Claude 在变化噪声下，给出标签后三份程序分别多成功 1、52、5 次。中间那一份几乎决定了平均差。它在没看到标签时把关抽屉的抓取点下移了 5–6.2 厘米，只成功 4/64，57 次失败被判为没关好抽屉。我在同一份程序里只把这两个高度偏移改回零，成功数回到 24/64。这个干预能解释这次严重退步的一部分。它并不能证明标签普遍有效。Codex 的三份起稿在新场景上合计只成功 1/192，单轮修复成绩也远低于原项目的多轮成绩。这个实验衡量一次修复，无法直接把历史五轮开发的收益拆成固定比例。[出问题的程序](../runs/noise_factorial/claude_r2/varied_hidden/proposal.py) · [只改高度的复测](../runs/noise_factorial/closing_intervention.json)

**在同一份冻结程序上改传感器，能看出它依赖什么。** 我又取了两代各 8 个 Claude 最终程序，各做同一批 32 个新布局。所有读数照常有误差时，两代分别成功 201/256、221/256。只把杯子位置和方向读准，分别为 216/256、231/256。只把抽屉和把手读准，则为 230/256、205/256，第二版的优势反转。其中一份第二版程序在正常误差下成功 31/32，只把把手位置读准就掉到 4/32，只把抽屉开度读准则是 32/32。至少这份程序对把手定位偏差极为敏感。后续调试应同时放入准确定位和带误差的情况，防止模型只适应其中一端。[分通道实验](../runs/sensor_ablation/results.json) · [同一程序的细分复测](../runs/sensor_ablation/close_height.json)

## Harness 改了什么

Codex CLI 和 Claude Code CLI 现在都能走同一条多任务开发流程。代理先交完整程序，控制器实际运行物理仿真，告诉它哪一项目标没完成、抓取后物体升高了多少、是否出现程序异常。下一轮从调试集上表现最好的已有版本继续改。另一份独立的验证集负责决定交哪一版。程序冻结之后，才打开测试集。每个候选、验证成绩和最终程序摘要都可追溯。[多任务控制器](../sim/multitask.py) · [CLI 接口](../sim/repair_cli.py)

在原抽屉任务上，我固定了两家代理各 8 次运行中实际提出过的程序，单独测试“怎么选最终版”。验证器用 16 个额外仿真布局挑版本，全程不再调用模型。Claude 在同一批测试中从 657/800 到 664/800（82.1% → 83.0%），Codex 从 559/800 到 581/800（69.9% → 72.6%）。Codex 最差的一轮从 21/100 回升到 48/100，另一轮从 70/100 降到 65/100。选版的实际价值是偶尔能捞回被后续修改破坏的程序。按开发轮次和测试场景成对重采样，两个平均增幅的区间仍都跨零。[同批候选的配对复测](../runs/selection_replay/results.json)

## 新任务和数据

从 LIBERO 官方仓库下载了任务定义、MuJoCo 资产和每项任务的 50 个初始状态。主实验使用 LIBERO-Long 全套 10 项任务。另从 LIBERO-90 留出 3 项，独立检查遇到新指令时是否值得再请 CLI 写一次程序。13 项任务共 650 个官方初始状态，核对后状态文件内的 650 行没有完全重复。分组是本项目自定的。策略能读取仿真物体名称、位置和区域，不需要从相机图像识别物体。[固定版本的上游数据](https://github.com/Lifelong-Robot-Learning/LIBERO/tree/8f1084e3132a39270c3a13ebe37270a43ece2a01/libero/libero) · [数据划分及复现命令](../docs/simulator_experiments.md)

主实验用 6 项任务开发，剩下 4 项任务在开发时完全留出。两家代理各产生 3 份候选程序，每份在每个开发任务上拿到 2 个调试初态。先用每项 2 个独立验证初态选版，又在相同候选池上评估全部 60 个验证初态以检查排名。完整任务要满足上游裁判的全部条件。只把壶放到了正确位置、炉子却没打开，仍然算失败。

Codex 的四项新任务全都没有完整成功，原因各不相同。“两把壶上炉”中，50 次终局时炉子都是开的（本轮重新检查发现，官方初态里炉子已经打开），45 次把第一把壶放对，第二把一次也没放对。奶酪和黄油装篮时，黄油有 44/50 次进篮，奶酪一次也没进去。“杯子上盘、布丁放盘右边”则 50 次都没发出任何动作。检查程序发现，它只会把“左盘、右盘”对应到杯子，遇到“盘子的右边”没有生成任何要执行的动作。前两项要排查第二个物体的抓放，后一项要先解决指令理解。[逐项判定和动作步数](../runs/long_codex_01/test_full.json) · [冻结程序](../runs/long_codex_01/policy_calibrated.py)

### 给新任务一次编程和调试机会

在另三项 LIBERO-90 任务上，我先让 Codex 根据指令和物体名称为每项任务改写一次程序，不给任何试跑。两种程序在每项 50 个相同初态上比较，直接运行原程序成功 4/150，只看文字改写成功 0/150。然后单独检验“允许少量仿真调试”：每项用 3 个初态看反馈、允许一次修复，再用另外 3 个初态选版本。下表只看三组程序都没有拿来调试或选版的 40 个初态。补充实验是在我们看过上一轮的汇总成绩后设计的，代理没有收到测试轨迹或测试成绩。这一组只用了 Codex。

| 新任务 | 直接复用 | 只看新指令改写 | 再给仿真反馈并选版 |
| --- | ---: | ---: | ---: |
| 开炉并把煎锅放上去 | 4/40 | 0/40 | 38/40 |
| 左碗叠右碗、再放入托盘 | 0/40 | 0/40 | 0/40 |
| 书放入收纳盒前格 | 0/40 | 0/40 | 0/40 |
| **合计** | **4/120** | **0/120** | **38/120** |

煎锅的反馈很具体：炉子已经打开，但夹爪从锅中央抓了两次，锅的提升高度都是零。修复程序改试锅沿，先小幅提升，再检查锅是否跟着移动，确认抓稳才往炉上送。叠碗和放书的验证集没有筛出能完整做对的版本。这两个任务是之后扩展抓取与放置技能时最值得保留的难例。[修复后的煎锅程序](../runs/transfer_codex_01/KITCHEN_SCENE3_turn_on_the_stove_and_put_the_frying_pan_on_it/repair/proposal.py) · [逐初态对照表](../runs/transfer_codex_01/scores_repaired.json)

**核验和限制。** 主实验与三个补充任务都使用 MuJoCo。公布的是完整任务成功数；炉子打开、锅没有放好只能得到部分进展。两个 CLI 都实际生成并修改了程序。Claude 主实验的第三次提议曾达到 6 分钟调用时限，保留已有两版并用相同提示重试；失败调用也消耗时间。仿真是真实执行的，没有使用真人示范或测试成功轨迹作为策略。冻结候选的完整代码、逐场景成败、关键配置和录像放入[实验凭证包](simulator_evidence.zip)。

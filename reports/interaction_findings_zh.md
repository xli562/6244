# 给 code agent 动作回执，能让一份程序做更多新题吗？

**工具被用起来了，也帮助过具体任务，但这轮没有测出稳定的整体提升。** Codex 在有无练习反馈两组的每个摆放上都取得相同的稳定结果。Claude 带反馈的平均稳定成功率多 1.2 个百分点，但在两份修改稿都能执行、初稿也真正做过动作的唯一一对里，带反馈的一组反而少成功 29 次。原来按题写程序的办法在两家模型上仍有较高成功率，代价是每来一道新题都要再调用模型。

## 稳定成绩

每个程序跑十道新题、每题 50 个相同摆放。主指标是官方判定成功之后，松开夹爪、抬手并等待共 40 步，目标依然成立。通用策略各生成三次，分母 1,500 包含同一组 500 个摆放的三次程序生成重复。

| 模型 | 通用初稿 | 同预算自查 | 同预算看反馈再改 | 原版逐题自由改写 |
|---|---:|---:|---:|---:|
| Codex | 719/1,500（47.9%） | 719/1,500（47.9%） | 719/1,500（47.9%） | 273/500（54.6%） |
| Claude | 84/1,500（5.6%） | 502/1,500（33.5%） | 520/1,500（34.7%） | 319/500（63.8%） |

按官方即时判分，Codex 三种通用策略各为 722/1,500，逐题参照为 274/500；Claude 分别为 85、503、522/1,500，逐题参照为 319/500。每种通用方案部署后都是零次模型调用。每个通用候选在开发时用两次模型调用，初稿跨自查和反馈组共享。逐题参照每个模型在测试题上共调用十次。两组通用修改的调用次数相等，反馈组的输入更长。

| 同一初稿的两个去向 | 第一次生成 | 第二次生成 | 第三次生成 |
|---|---:|---:|---:|
| Codex 自查 → 看反馈 | 223 → 223 | 223 → 223 | 273 → 273 |
| Claude 自查 → 看反馈 | 275 → 246 | 227 → 0 | 0 → 274 |

上表每格分母是 500。Claude 第二、三份初稿均超过原有 600 秒上限，因此这两份初稿的练习记录只有错误，没有机械臂动作。第二份反馈修改稿使用了自己类中的私有属性 `self._desc`，触发原策略检查器的统一限制；第三份自查修改稿超时。两份无效的修改稿各按 0/500 计入主结果，没有补调。不能把这两对的分差解释成“机器人看了物理反馈之后学会了”。

## 哪些改动有效，哪些没用

- **布丁放进抽屉再关好。** 在 Claude 第一对可执行修改稿中，自查版是 0/50，反馈版是 18/50。反馈版写出一条可复用的规则：测到提起不足 1.5 厘米，就跳过后续相同抓法。动作记录显示，自查版在全部 50 个摆放都重复请求了普通抓放，反馈版每个摆放只请求一次，给其他动作留下步数。两份程序还有其他差别，18 次的增益不能全部归给这一条规则。
- **取中间的碗放上柜顶。** 同一对 Claude 程序从 50/50 降至 0/50。自查版 50 次选的是任务要求的 2 号碗，反馈版 50 次都选了 1 号碗，目的地仍然相同。动作回执能告诉程序“我抓的这个碗动了”，却无法直接告诉它“我理解错了中间指的是谁”。
- **平底锅上柜顶。** Claude 第一对通用程序 50 次都在发出动作前结束；旧版逐题程序把题面中的平底锅和柜顶对应到了场景里的具体名字，稳定完成 43/50。这里的障碍在动作执行之前，单靠抓取后的反馈没有机会补救。
- **工具实际被使用，但使用量和成绩是两回事。** Codex 反馈组在 1,150/1,500 次试跑调用了新动作接口，三个重复里自查与带反馈的逐摆放成败完全一致。两组共享工具，所以本实验可以比较“额外收到练习反馈”的效果，无法单独估计动作接口相对无工具版本的贡献。
- **测试数据有一处文字与判分冲突。** 白杯那题的原始指令写的是收纳盒“右格”，官方目标却是收纳盒右边的桌面区域。主要成绩按预先约定的官方目标保留，各组此题均为零。只看其余九题，Codex 自查与反馈仍同为 719/1,350，Claude 仍是 502 对 520/1,350。不能凭这题判定模型误解了用户语言。
## 为什么做这个实验

三项 2026 年工作提供了不同的出发点：

- **CaP-X** 比较了编程接口的抽象程度，也研究了多轮执行反馈。本项目据此把“工具可用”和“模型修改代码前看到了什么”分开比较。[原文，2026 年 3 月提交、7 月修订](https://arxiv.org/abs/2603.22435)
- **ASPIRE** 让编程 agent 根据执行轨迹改程序，并把经验积累进技能库。本项目关心其中更小的一个问题：只给一次修改机会，看见动作造成的物理变化，是否就足以帮助下一道题。[作者项目页，2026 年](https://research.nvidia.com/labs/gear/aspire/)
- **ACE-CaP-0** 研究怎样把开发阶段的交互经验留在冻结程序中，从而减少运行中的模型调用。本项目把这个问题搬到纯模拟环境，要求固定程序读懂部署时才出现的指令。[预印本，2026 年 11 月 12 日](https://arxiv.org/abs/2611.16872)

这次自行实现的部分是动作字典和物理回执，以及对同一份初稿的配对比较。模型能写出“找出目标对象 → 执行一个动作 → 检查物体实际位移 → 在剩余预算内决定下一步”的程序。动作记录既供 Python 在现场决策，也可以在练习后交给 code agent 审查。实验没有使用论文的代码、演示或训练权重。

## 怎样检验迁移

使用原有抓取版的机械动作和判分器。新接口公开场景里的物体、固定装置和区域类别、区域所属实体、剩余步数，以及实际执行动作的测量结果。动作前后位置属于模拟器状态观测，这项实验不考核视觉感知。开发反馈里没有官方目标谓词、得分或成功标签。模拟器仍会在官方成功时提前终止，模型可能据此从步数间接推断完成情况。

每家模型各生成三份独立初稿。每份初稿练习八道旧题，每题两个摆放。随后同一份初稿分两路：自查组看程序，反馈组额外看同一程序的 16 条物理记录。两边都只写一次初稿、修改一次，使用同样的模型、推理设置、动作和 500 步预算。初稿在两路之间共享，实际共调用模型 18 次。新题上两路都不再调用模型。另用旧 harness 对每家模型、每道新题做一次自由改写，共 20 次模型调用。这组衡量继续逐题写程序的实际效果，调用预算与通用策略不同。

新题从固定版 LIBERO-90 的厨房、客厅和书房按事先指定的哈希顺序抽取，每个房间最多四个不同场景。排除了目前 60 道历史任务和完全相同的标准化英文指令。书房满足去重条件后抽到两个场景，共十题。每题跑全部 50 个官方摆放。500 个测试初态互不相同，与历史 3,000 个初态无完全相同的状态向量。上轮 30 题纯测试集没有用于开发。本次采用同一模拟器，部分题目的动作语义相似，例如两道题都要求把碗放上柜顶。参照组逐题收到指令；通用程序在部署执行时才读到指令。提示、候选代码及两组输入差异均可复核。[实验清单](../harness/interaction/manifest.json) · [固定版官方任务](https://github.com/Lifelong-Robot-Learning/LIBERO/tree/8f1084e3132a39270c3a13ebe37270a43ece2a01/libero/libero/bddl_files/libero_90)
